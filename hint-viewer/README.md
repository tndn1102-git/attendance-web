# 락다운시티 힌트폰 GM 뷰어

동시에 돌아가는 힌트폰(`fantastrick.co.kr/hint-phone/`) **2대**와 상태를 공유하며,
진행을 실시간 모니터링하고 원격 조작하는 GM용 뷰어. Cloudflare Worker로 서빙.

## 왜 Worker인가
- Cloudflare는 HTTPS → 브라우저가 `ws://`(비암호 8080)에 직접 못 붙음(mixed-content 차단).
- Worker가 **wss(브라우저) ↔ ws(8080)** 브릿지 + 정적 페이지 서빙을 겸함.

## 구조
```
[GM 브라우저] --wss--> [Cloudflare Worker] --ws:8080--> [iptime 릴레이] <--master--> [힌트폰 x2]
     뷰어 UI            /(HTML) /live(브릿지)          (simPin 패치)        (v141 패치)
```

안전가옥 ①(pin23) → ②(pin25) 를 0.6초 안에 연속 태그하면 이전 단계의 `display:'none'`(600ms) 이

반대로 **옛 미션이 뒤늦게 튀어나와** 최신 미션을 덮었고, 게임 도중 재시작하면 스냅샷 재생으로 이게 한꺼번에 터졌다.

**조치(v140)** — `app.js` 의 표시 계층을 스케줄러로 교체했다. 자세한 규칙은 `PROTOCOL.md`.
- 지우기는 타이머 없이 `hide` 클래스만 (뒤늦게 화면을 지우는 타이머 자체를 없앰)
- 칸(mission/details/location/inprogress)마다 **세대(generation)** — 최신 단계가 항상 이긴다
- 표시할 때 `hide` 를 반드시 제거 (`.hide` 가 `.show` 뒤에 선언돼 둘 다 붙으면 투명해짐)
- SNS 개방 같은 **게임 진행 처리는 `sideEffect`** 로 분리 — 화면 표시가 취소돼도 실행된다
- 스냅샷 재생은 연출 없이 **진행 순서(`rank`)로 최종 상태만** 즉시 그린다

## 2026-08-03 추가: 태블릿 시간 자동 동기화 (v141)

폰이 게임 도중 재시작되면 진행은 스냅샷으로 따라잡지만 **타이머는 복구할 길이 없어 1:40:00 부터 다시 셌다.**
GM 이 [시간 적용]으로 손수 맞추기 전까지 손님은 틀린 시간을 봤다.

**조치(v141)** — 살아 있는 다른 태블릿에서 받아온다. 서버 수정 불필요(simPin 채널 재사용, `__timereq__` / `__timeres__`).
- 재시작한 폰이 접속 즉시 물어보고, 못 받으면 **10초마다** 다시 묻는다(다른 태블릿을 나중에 켜도 맞춰짐)
- **신뢰(synced)** 개념이 핵심 — 응답도 채택도 "믿을 만한" 폰만 한다.
  스냅샷 재생으로 시작된 타이머(= 재시작 복구본)는 **못 믿는 값**으로 표시(`tU-`)해 절대 퍼뜨리지 않는다.
  없으면 재시작한 폰끼리 틀린 1:40:00 을 주고받아 둘 다 확신하는 오답이 된다.
- 이미 아는 폰은 남의 보고에 흔들리지 않는다(양쪽 다 벽시계 기준이라 드리프트 없음)
- 자동 동기화는 ack 를 보내지 않는다 — 뷰어에 GM 이 누르지도 않은 "✔ 폰 적용" 이 뜨면 안 되므로
- **뷰어**: 못 믿는 폰(`tU-`)의 보고로 시계를 바꾸지 않고 "미동기화"로 표시, 두 폰이 5초 넘게 어긋나면 "폰 시간 불일치" 경고

검증: `test/reset.test.mjs` I1~I25 (신뢰 판정 / 응답·채택 규칙 / 릴레이 경유 2대 연동 / 뷰어 표시 / 하위호환)
+ `test/phone-display/live-timesync.test.mjs` — **라이브 파일로** 폰 2대를 띄워 실제 복구까지 확인(매장 릴레이에는 접속 안 함)

## 2026-08-04 수정: 종료 신호 뒤 시간이 다시 흐른다 (v142)

엔딩·TIME OUT 이면 폰·뷰어 모두 시간이 **끝까지 멈춰** 있어야 하는데, 멈췄다가 중간에 다시 흐르거나
아예 안 멈추는 경우가 있었다. 원인은 정지가 "상태"로 남지 않은 것.

- 폰은 `clearInterval` 만 하고 `timerInterval`·`endTime` 을 그대로 뒀다
  → `endTime` 이 남아 **`restoreTimer()`(ws 재연결마다 호출)** 가 타이머를 도로 켰고,
    `timerInterval` 이 truthy 로 남아 `_gmApplyTime`(시간 적용·자동동기화)도 "진행 중"으로 오해해 다시 켰다
- **뷰어는 엔딩에 플래그만 켜고 시계는 멈추지도 않았다.** 게다가 폰이 계속 보내는 `__time__` 을 받을 때마다
  `tStart()` 를 불러, 멈춰 있던 시계까지 10초마다 되살렸다

**조치(v142)** — 정지를 상태로 남기고(폰 `timerStopped`, 뷰어 `ended`) **켜는 쪽이 전부 그 값을 확인한다.**
`startTimer()`·`restoreTimer()`·뷰어 `tStart()` 경로가 모두 막힌다. 해제는 **초기화로만** 된다.

검증: `test/reset.test.mjs` J1~J14(뷰어) + `test/phone-display/timerstop.test.mjs` 16건
(폰 — ws 재연결·시간적용·TIME OUT·초기화 후 재사용)

## 2026-08-05 수정: 엔딩인데 한 대만 멈춤 / 재시작한 태블릿이 시간을 못 받음 (v143)

같은 날 두 건이 들어왔고, 뿌리가 서로 얽혀 있었다.

### ① 엔딩 화면이 떴는데 한 대는 타이머가 안 멈춘다

v142 의 확정 정지(`timerStopped`)는 맞는 조치였다. 문제는 **그 태블릿이 아직 v141 페이지를
열어둔 채였다는 것** — v142 는 08-04 밤에 올렸지만 "태블릿 2대 새로고침"이 안 됐다.
v141 은 엔딩에 `clearInterval` 만 하고 `endTime` 을 남겨서, **ws 재연결마다 도는
`restoreTimer()` 가 타이머를 도로 켠다.** 그 한 대만 계속 흐른 이유가 이것이다.

고칠 것은 코드가 아니라 **"구버전 태블릿이 남아 있어도 아무도 모른다"** 는 구멍이었다.

- **버전 보고(`__ver__`)** — 폰이 5초마다 자기 버전을 보고하고, 뷰어 헤더에 `폰 v143 ×2` 를 항상 띄운다.
  한 대가 구버전이면 `⚠ 구버전 1대` 로 빨갛게 뜬다(구버전은 `__ver__` 를 안 보내므로 대수 차이로 잡힌다).
- **종료 공유(`__end__`)** — 엔딩·TIME OUT 을 폰끼리 알린다. 한 대가 종료 핀을 놓쳐도 함께 확정 정지한다.
- **뷰어 감시** — 엔딩 뒤에도 남은시간이 줄어드는 폰을 잡아 경고하고, `[⏹ 엔딩 정지 재전송]` 버튼을 띄운다.
  (구버전 태블릿은 이 신호도 무시하므로 그때는 새로고침밖에 없다 — 그래서 버전 표시가 먼저다)

### ② 게임 도중 꺼진 태블릿이 다시 켜졌는데 시간이 안 맞고 초기화면으로 갔다

원인은 **부팅 통보**였다. v142 까지는 폰이 어떤 이유로 켜지든 똑같이 `__reset__` 을 쐈다.
그래서 사고 재시작 한 번에

1. 멀쩡히 돌던 **다른 태블릿이 새로고침**돼 연결모드 대기화면(= 초기화면)으로 가고
2. 뷰어의 진행·힌트·타이머까지 통째로 지워지고
3. 그 바람에 **시간의 기준(`tS-`) 이 사라져** 재시작한 폰은 물어볼 상대조차 없어졌다

거기에 GM 이 [게임 시작 신호]를 다시 보내면 더 나빠졌다 — 재시작한 폰이 그 `pin22` 를
"내가 본 게임 시작"으로 믿고 **1:40:00 을 정답(`tS-`)으로 퍼뜨려** 뷰어 시계까지 되돌렸다.

**조치(v143)**
- 부팅 통보를 **6초 유예**하고, 그 사이 게임이 돌고 있다는 증거(스냅샷의 pin22 / `tS-` 폰의 시간 보고)가
  보이면 **취소**한다 → 아무것도 지워지지 않고, 시간 기준이 살아남아 자동 동기화가 정상 작동한다.
  대신 `__boot__` 로 뷰어 로그에만 "폰이 재시작됨"을 남긴다.
- 10탭·원격 초기화로 인한 새로고침은 종전대로 즉시 확실하게 전파한다(명시적 지시라 판정하지 않는다).
- `pin22` 라이브 관측은 ⓐ 이 폰이 아직 시작을 모르고 ⓑ 부팅 판정이 끝났고 ⓒ 진행 중인 게임이 아닐 때만 신뢰한다.
- 부팅 직후 `__timereq__` 를 1.5초 간격 8회로 더 보낸다(10초는 손님이 알아볼 만큼 길다).

**동기화 기준(질문에 대한 답)**: 기준은 **`tS-` 로 표시된 폰**이다.
`tS-` 가 되는 길은 ⓐ 게임 시작 핀을 라이브로 봄 ⓑ GM 이 [시간 적용] ⓒ 이미 `tS-` 인 폰에게서 받아옴, 셋뿐이다.
스냅샷으로 복구한 폰은 `tU-` 이고, **응답도 채택도 `tS-` 만** 한다. 뷰어도 `tS-` 보고만 따른다.

검증: `test/reset.test.mjs` L1~L15(부팅 판정·버스트·버전) · M1~M7(시작신호 재전송) · N1~N16(종료 공유·뷰어 감시)

### 2026-08-02 사고: "뷰어와 태블릿 시간이 다르다"
뷰어의 시간 적용이 `{type:'timeSync'}` 라는 **독자 타입**으로 나갔는데, 매장 서버에 실제로 적용된
패치본(`server.patched.zip`, 07-28 16:22)에는 그 블록이 **없었다**. 로컬 `server.patched.js` 에만
47분 뒤 추가하고 zip·문서를 다시 만들지 않은 것. 서버는 모르는 타입을 조용히 버려서 **폰에 아무것도
도착하지 않았고**, 반대로 폰→뷰어 시간보고(`__time__`)는 simPin 채널이라 멀쩡히 동작해서
뷰어가 10초 뒤 폰 시간으로 되돌아갔다 → "다르다"로 보임.

**조치(v139)**: 시간 세팅을 이미 패치된 **simPin `__settime__` 채널**로 옮김 → **서버 수정 불필요**.
더불어 폰이 `__timeack__` 로 적용을 회신하고, 3초 내 회신이 없으면 뷰어가 **"✖ 폰 적용 실패"** 를
표시한다(조용한 실패 재발 방지). `timeSync` 경로도 호환용으로 계속 지원.

## 공유 상태 — 힌트폰 2대 + 뷰어 (v139)

힌트폰 **2대가 동시에** 돌아간다. 2대와 뷰어가 하나의 상태를 공유한다.

**초기화** — 아무 폰이나 좌측 하단 **10탭** → 그 자리에서 **다른 폰 + 뷰어가 즉시 초기화**되고,
이 폰은 새로고침돼 **연결모드 버튼 화면에서 대기**한다. 팀 교대 때 폰 하나만 만지면 된다.
(연결모드 버튼을 눌러 재접속할 때 중복 초기화는 일어나지 않는다)

초기화되는 것: 메인 진행·업적 퀘스트·상태 플래그 / 타이머(1:40:00 정지, 예약된 137초 시작 취소)
/ 폰 시간동기 표시 / 개인 SNS·DM / 수신 카운터. 뷰어 상단에 초기화 알림 토스트가 뜬다.

**SNS/DM** — 한 폰에서 터치(15탭/10탭)로 켜면 다른 폰에도 자동 활성화. 뷰어 버튼은 2대 전부에 적용.
뷰어는 "**● 활성 1/2대**"처럼 **폰 대수로 집계**해 보여준다.

**힌트 사용 개수** — 힌트 모달 ENTER 버튼 아래에 "USED n회". 같은 힌트를 다시 봐도 안 오르고(고유 힌트만),
폰 2대가 개수를 공유한다. 뷰어에는 개수 + 어떤 코드를 몇 시에 봤는지까지 남고 3회 노랑·5회 빨강.

- 초기화 통보는 **페이지 로드당 1회**만 → 게임 중 ws가 끊겼다 재연결돼도 안 지워진다.
- 통보를 **받은** 폰도 새로고침으로 초기화된다 → 양쪽 다 연결모드 버튼 화면에서 대기.
  (표식을 남겨 되받아치지 않으므로 폰끼리 무한 초기화는 없다)
- **DM이 "1/2대"로 보이는 건 정상.** DM 활성은 그 폰에서 DM 탭을 열면 꺼지는 알림 플래그라
  꺼짐은 전파하지 않는다(한쪽이 읽었다고 다른 폰 알림을 지우면 안 되므로).
- **새로고침의 "이유"를 구분한다**(v138): 10탭·원격 초기화로 인한 새로고침은 슬레이브 스냅샷을 무시해
  깨끗한 대기 상태가 되고, 그 밖의 새로고침(배터리·앱 종료·오탭)은 스냅샷으로 **진행을 따라잡는다**.
- ⚠ 그래도 폰이 사고로 재시작되면 부팅 통보가 나가 **양쪽 폰과 뷰어가 초기화된다**(선택한 모델의 이면).
- 필요 조건: **두 태블릿 모두** `websocket.js` **v141** + 서버 simPin 패치.
- 뷰어 헤더의 **[진행 초기화]** 버튼은 뷰어 화면만 초기화한다(폰에는 안 나감).
