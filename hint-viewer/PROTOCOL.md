# 프로토콜 (뷰어 ↔ Worker ↔ 8080 릴레이 서버)

실제 `server.js` 확인 후 확정. 힌트폰 앱은 `websocket.js` 만 패치하고 `app.js` 는 **무수정**으로 둔다.

## 연결 경로
```
[GM 브라우저] --wss--> [Cloudflare Worker /live] --ws:8080--> [iptime 릴레이 서버] <--ws-- [힌트폰=master]
```
- Cloudflare는 HTTPS라 브라우저가 `ws://`에 직접 못 붙음(mixed-content) → Worker가 wss↔ws 브릿지.
- Worker는 8080에 붙는 즉시 `{"type":"master"}` 를 보냄.

## 왜 master 인가 (observer 아님)
서버 `broadcastToMasters`는 `type==='master'` **전부**에 뿌린다(소켓별 Map, 단일 master 덮어쓰기 없음).
→ 뷰어가 master로 하나 더 붙어도 **실폰 kick 없음**. observer 같은 별도 역할이 필요 없다.

## 서버 → 뷰어(master) 수신
- 접속 직후: `{"type":"slaveList","slaves":[{"slaveID","slaveNickname","arduinos":[{"arduinoID","pins":[{"pin","state"}]}]}]}` (스냅샷)
- 슬레이브 등록 시: `{"type":"slaveRegister","slaveID","arduinos":[...]}`
- 핀 변화: `{"type":"update","slaveID","arduinoID","updates":[{"pin","state"}]}`
- 아두이노 해제: `{"type":"arduinoDisconnect","slaveID","arduinoID"}`

뷰어는 이걸 힌트폰 `checkPinStatus`와 동일한 상태머신(statemachine.js)에 먹여 진행을 복제한다.

## 뷰어(master) → 서버 (조작, simPin 패치 필요)
- `{"type":"simPin","slaveID","arduinoID","pin":N,"state":"on"}`
- 서버(패치본)가 이를 `{"type":"update",...}` 로 바꿔 **모든 master(폰 포함)** 에 브로드캐스트 → 폰 진행.
- **물리 아두이노(slave)로는 안 감**(command 아님). 무장(ARM) + 확인창을 거쳐서만 전송.

## 폰 → 뷰어 내부 채널 (simPin 재사용, `__` 접두 = 게임 로직과 절대 안 겹침)
| slaveID | 방향 | 내용 |
|---------|------|------|
| `__time__` | 폰 → 뷰어·**다른 폰** | 타이머 도는 동안 10초마다 남은 초 (`pin` = 초). `arduinoID` = `tS-xxxx`(믿을 만함) / `tU-xxxx`(모름) |
| `__timereq__` | 폰 → 다른 폰 | **"나 시간 모른다, 알려줘"** (재시작 복구) |
| `__timeres__` | 폰 → 다른 폰 | 시간 응답 (`pin` = 남은 초, `arduinoID` = `tS-xxxx`) |
| `__status__` | 폰 → 뷰어 | 5초마다 SNS/DM 활성 비트 (`pin` = 1:SNS + 2:DM) |
| `__snsctl__` | 뷰어 → 폰, **폰 → 폰** | SNS(1)/DM(2) 활성화 |
| `__reset__` | 폰 → 뷰어·**다른 폰** | **초기화 통보** (`pin` 1 = 새로고침·부팅, 2 = `resetScreen()`) |
| `__hint__` | 폰 → 뷰어·다른 폰 | **방금 새로 본 힌트** (`pin` = LC 코드 번호 1~21) |
| `__hintmask__` | 폰 → 뷰어·다른 폰 | 5초마다 힌트 사용 **전체 비트마스크** (비트 0 = LC001) |
| `__settime__` | 뷰어 → 폰 | **타이머 세팅** (`pin` = 맞출 남은 초) |
| `__timeack__` | 폰 → 뷰어 | 시간 세팅을 **적용했다는 회신** (`pin` = 적용된 초, `arduinoID` = `ack-xxxx`) |
| `__end__` | 폰 → **다른 폰**, 뷰어 → 폰 | **종료 확정 정지** (`pin` 1 = 엔딩, 2 = TIME OUT, `arduinoID` = `end-xxxx`) — v143 |
| `__ver__` | 폰 → 뷰어 | 5초마다 **패치 버전** (`pin` = 143, `arduinoID` = `v-xxxx`) — v143 |
| `__boot__` | 폰 → 뷰어 | **게임 도중 재시작함**(초기화 아님) 알림 (`arduinoID` = `rb-xxxx`) — v143 |

- 양쪽 다 `slaveID` 가 `__` 로 시작하면 게임 상태머신에 넣지 않는다(에코 무시).
- `arduinoID` 에 **보낸 폰의 식별자**를 실어 보낸다(`snsdm-xxxx` / `boot-xxxx` / `ctl-xxxx`).
  서버는 slaveID·arduinoID 를 그대로 통과시키므로 **서버 수정 없이** 폰을 구분할 수 있다.

## 공유 상태 — 힌트폰 2대 + 뷰어

힌트폰 2대가 동시에 돌아간다. 셋이 하나의 상태를 공유하도록 아래 규칙을 지킨다.

| 항목 | 어떻게 공유되나 |
|---|---|
| 게임 진행 | 릴레이가 같은 핀 이벤트를 모든 master 에 뿌림 → 자동으로 동일 |
| 타이머 | 같은 pin22 로 동시 시작. 뷰어 `timeSync` 는 모든 폰에 동시 적용 |
| SNS/DM 활성화 | 한 폰에서 터치로 켜면 `__snsctl__` 로 다른 폰·뷰어에 전파 |
| 초기화 | 한 폰을 새로고침하면 `__reset__` → 다른 폰 초기화 + 뷰어 초기화 |

### 10탭은 "통보 먼저, 새로고침 나중" (v134)
app.js 의 10탭 핸들러는 곧바로 `location.reload()` 를 부른다. 그러면 통보가 나가기 전에 페이지가 날아가서
**새로고침 후 "웹소켓모드" 버튼을 눌러 재접속한 다음에야** 초기화가 전파됐다.

패치 스크립트는 `index.html` 에서 app.js 보다 **먼저** 로드되므로 같은 영역(`#refreshTouchArea`)의
클릭 리스너도 먼저 붙는다. 이걸 이용해 순서를 뒤집는다:

1. 우리 리스너가 먼저 받아 `stopImmediatePropagation()` 으로 **app.js 의 즉시 reload 를 차단**
2. 10번째 탭에서 `__reset__` 을 **먼저 전송** → 다른 폰·뷰어가 그 자리에서 초기화
3. 서버가 되돌려준 **자기 에코를 확인한 뒤** 새로고침(전송 유실 방지). 에코가 안 오면 **1.5초 폴백**으로 반드시 새로고침
4. `sessionStorage` 플래그로 **새로고침 후 부팅 통보를 생략** → 연결모드 버튼을 눌러도 중복 초기화 없음

결과: 10탭 → 다른 폰·뷰어 즉시 초기화, 이 폰은 연결모드 버튼 화면에서 대기.

### 무한 루프·유실을 막는 규칙
1. `__reset__` 은 **페이지 로드당 1회만**. ws 재연결(끊김 복구)에는 안 보낸다 —
   게임 중 네트워크가 잠깐 끊겼다고 전부 지워지면 안 되기 때문.
2. `__reset__` 을 **받은** 폰도 `location.reload()` 로 초기화하되, 새로고침 직전에
   `sessionStorage._gmResetSent` 표식을 남겨 **다시 통보하지 않는다.**
   (v133~134 에서는 `resetScreen()` 소프트 리셋을 썼지만, 그건 `pinProgress` 만 비워서
   5초 뒤 슬레이브 스냅샷이 진행을 통째로 재생 → 화면 겹침 + 자동 시작을 만들었다.)
3. `arduinoID` 의 폰 식별자로 **자기 에코를 무시**한다. **정확 비교**(부분일치 금지) —
   부분일치면 식별자가 우연히 겹칠 때 그 폰만 초기화되지 않는다.
4. 통보 전송에 **성공했을 때만** 표식을 남긴다. 연결이 끊긴 상태에서 10탭하면 통보를 못 보내는데,
   표식만 남기면 재접속 후에도 전파되지 않아 **초기화가 통째로 유실**된다.

### 슬레이브 스냅샷은 재생하지 않는다 (v135~137)
슬레이브는 **5초마다 재등록**하며 전체 핀 스냅샷을 다시 뿌린다. 이걸 그대로 게임 로직에 먹이면
초기화로 진행을 비운 직후 통째로 재생돼 **화면이 겹치고 게임이 저절로 시작**된다(뷰어는 5초 뒤 되살아남).
폰·뷰어 모두 핀별 마지막 상태를 기억하고 **값이 바뀐 핀만** 반영한다.

부팅 시점에 이미 걸려 있던 핀(처음 보는 핀)의 처리는 **새로고침 이유에 따라 갈린다**:

| 새로고침 이유 | 첫 스냅샷 | 이유 |
|---|---|---|
| 10탭·원격 초기화 | 무시 | 지운 진행이 되살아나면 안 됨 |
| 그 밖(사고·앱 재시작) | 반영 | 게임 도중 죽었다 살아난 폰은 진행을 따라잡아야 함 |

구분은 `sessionStorage._gmResetSent` 표식으로 한다(초기화 새로고침 직전에 남기고, 다음 로드에서 `_gmBootWasReset` 으로 소비).
뷰어는 항상 첫 스냅샷을 반영하되(게임 중 열어도 따라잡기) 초기화 후에는 기억을 유지해 되살아나지 않는다.

### 힌트 사용 개수 (v138)
힌트 코드는 **LC001~LC021 (21개)**. 21개를 **비트마스크 정수 하나**로 들고 다닌다(비트 0 = LC001).

- **고유 힌트만 집계** — 같은 코드를 다시 봐도 개수는 안 오른다(비트마스크라 구조적으로 보장).
- 폰이 힌트를 새로 열람하면(`showHintDetail`) `__hint__` 로 즉시 알리고,
  5초마다 `__hintmask__` 로 전체 목록을 흘린다 → **폰 2대가 같은 개수를 공유**하고,
  새로고침으로 목록을 잃은 폰도 다른 폰의 마스크로 **자동 복구**된다.
- 뷰어는 `__hint__` 로 코드·시각을 남기고, `__hintmask__` 로 개수를 보정한다
  (뷰어를 늦게 열어도 개수는 맞고, 그 전 힌트는 시각만 없다). 3회부터 노랑, 5회부터 빨강.
- 폰 표시는 힌트 모달 **ENTER 버튼 아래**(top 80.5%). `app.js`·`styles.css` 는 안 건드리고
  `websocket.js` 가 `<style>` 과 요소를 주입한다. 힌트 상세화면에서는 숨긴다.
- 초기화(새로고침)하면 메모리째 0으로 돌아간다.

### SNS/DM 전파는 "켜짐"만
`isSNSDMActivated` 는 DM 탭을 열면 스스로 꺼지는 **알림 플래그**다(app.js `clickDM`).
그래서 켜짐(0→1)만 전파하고 꺼짐은 전파하지 않는다 — 한쪽 플레이어가 DM 을 읽었다고
다른 폰의 알림까지 지우면 안 되기 때문. **뷰어에 "DM 1/2대"로 보이는 건 정상이다.**

### 시간 세팅은 `timeSync` 가 아니라 `__settime__` 로 간다 (v139)

`{"type":"timeSync","seconds":N}` 이라는 **독자 메시지 타입**을 만들어 뒀지만, 매장 릴레이 서버에 적용된
패치본에는 그 블록이 **없다**(`server.patched.zip` = 07-28 16:22, simPin 만 포함. timeSync 는 47분 뒤
로컬 `.js` 에만 추가되고 zip·문서는 다시 만들지 않았다). 서버는 모르는 타입을 조용히 버리므로
**뷰어에서 시간을 넣어도 폰에 아무것도 도착하지 않았다** — 에러도 로그도 없이.

반대 방향(`__time__` 폰→뷰어 보고)은 simPin 채널을 재사용해 **정상 작동**했기 때문에,
뷰어가 10초 뒤 폰 시간으로 되돌아가 "뷰어와 태블릿 시간이 다르다"로 보였다.

→ 시간 세팅도 **이미 패치돼 있는 simPin 채널**(`__settime__`)로 옮겼다. **서버를 건드릴 필요가 없다.**
`timeSync` 도 함께 보내고 폰도 계속 받아준다(서버가 나중에 패치되면 그 경로로도 도달, 동작은 동일).

**적용 확인(ack)이 규격의 일부다.** 폰은 시간을 반영한 즉시 `__timeack__` 로 회신하고,
뷰어는 3초 안에 회신이 없으면 **"✖ 폰 적용 실패"** 를 띄운다. 조용한 실패가 이번 사고의 본질이었다.

⚠️ 폰은 **타이머가 이미 돌고 있을 때만** `startTimer()` 로 다시 켠다. 시작 전(대기화면)에는 값·표시만
바꾼다 — 대기 중에 카운트다운을 시작해 버리면 정작 게임이 시작되는 `pin22 + 137초` 시점에는
그만큼 깎여 있다(`app.js:635` 는 `timeRemaining` 을 리셋하지 않고 그대로 쓴다).

### 미션/디테일 표시는 "예약"이 아니라 "상태" (v140)

폰의 미션·디테일 칸이 **플레이 중간중간 비어 있는** 사고가 있었다. 원인은 프로토콜이 아니라 폰 `app.js` 의 표시 구조였다.

단계마다 `setTimeout` 체인으로 `hide → display:'none'(600ms) → reveal(2~30초)` 을 예약해두고 **그 예약을 취소하지 않았다.**
그래서 단계가 겹치면
- 이전 단계의 `display:'none'` 이 **새로 뜬 미션을 지우고**(다음 핀이 올 때까지 공백)
- 이전 단계의 늦은 reveal 이 **최신 미션을 옛 미션으로 되돌렸다.**

안전가옥 ①(pin23) → ②(pin25) 를 **0.6초 안에** 연속 태그하면 100% 재현됐다(릴레이가 두 핀을 한 `updates[]` 로 보내면 확정).
대기가 긴 단계(엔비바③ 20초 · 안전가옥④ 30초 · ⑤ 15초 · ⑥ 30초 · 박사방③ 10초 · 게임시작 137초) 안에서 다음 카드를 찍으면 항상 위험했다.

v140 의 규칙:
1. **지우기는 타이머를 쓰지 않는다.** `hide` 클래스만 붙인다(`fadeOutScale forwards` 로 이미 투명) → 뒤늦게 화면을 지우는 타이머 자체가 없다.
2. **칸마다 세대(generation)** — `mission` / `details` / `location` / `inprogress` 를 따로 관리한다. 새 단계가 건드린 칸의 예약만 무효가 되므로,
   디테일만 바꾸는 단계(소독실 단서 등)가 진행 중인 메인 미션 예약을 죽이지 않는다.
3. **표시할 때 `hide` 를 반드시 제거한다.** `styles.css` 에서 `.hide` 가 `.show` **뒤에** 선언돼 특정도가 같아,
   둘 다 붙으면 `display:block` 인데 투명해진다(= 안 뜬 것처럼 보임).
4. **게임 진행 처리는 `sideEffect` 로 분리** — 화면 표시가 취소돼도 반드시 실행된다.
   (안전가옥 ④ 의 SNS 개방이 30초 대기 중에 다음 카드를 찍었다는 이유로 유실되면 게임이 막힌다)

### 스냅샷 재생은 진행 순서로 (v140)

`slaveRegister` 스냅샷 재생 중에는 `window.__ldcCatchUp = true` 를 세워 **연출·효과음·대기 없이 최종 상태만** 그린다.
스냅샷은 슬레이브마다 따로(최대 5초에 걸쳐) 오고 **그 도착 순서가 게임 진행 순서와 무관**하므로,
도착한 대로 그리면 진행이 뒤로 간다(엔비바 ③ 이 안전가옥 ⑥ 을 덮는 식).
그래서 각 단계에 **`rank`(뷰어 `statemachine.js` 의 STEPS 순서와 동일)** 를 달고, 칸마다 가장 진도가 나간 단계를 골라 한 번에 그린다.

⚠ 단계를 추가하거나 순서를 바꾸면 `app.js` 의 `rank` 도 같이 고쳐야 한다.

### 태블릿 시간 자동 동기화 (v141)

폰이 게임 도중 재시작되면 스냅샷으로 **진행은** 따라잡지만, 타이머는 복구할 길이 없어 1:40:00 부터 다시 셌다
(`__time__` 은 폰→뷰어 단방향 보고였다). GM 이 [시간 적용]으로 손수 맞추기 전까지 손님은 틀린 시간을 봤다.

폰은 2대가 늘 같이 돌아가므로 **살아 있는 쪽에서 받아온다.** 서버 수정은 필요 없다 — simPin 채널을 그대로 쓴다.

```
재시작한 폰 --__timereq__--> [릴레이] --> 다른 폰
재시작한 폰 <--__timeres__-- [릴레이] <-- 다른 폰 (믿을 만할 때만)
```

**신뢰(synced)가 이 설계의 핵심이다.** 없으면 재시작한 폰끼리 틀린 1:40:00 을 주고받아 "둘 다 확신하는 오답"이 된다.

| synced | 언제 |
|---|---|
| true | 게임 시작(pin22)을 **라이브로** 봤다 / GM 이 `__settime__` 으로 세팅했다 / synced 인 다른 폰에서 받아왔다 |
| false | **스냅샷 재생**으로 시작된 타이머 (= 재시작 복구본) — 못 믿는다 |

- **응답도 채택도 synced 인 쪽만** 한다. `arduinoID` 의 `tS-`/`tU-` 접두로 구분한다.
- 이미 synced 인 폰은 남의 보고에 흔들리지 않는다. 두 폰 모두 `endTime` 을 벽시계로 계산하므로 드리프트 보정이 필요 없다.
- 모르는 동안 **10초마다** 다시 물어본다 → 다른 태블릿을 나중에 켜도 그때 맞춰진다.
- 자동 동기화는 `__timeack__` 을 **보내지 않는다**. 보내면 뷰어에 "✔ 폰 n대 적용" 이 GM 이 누르지도 않았는데 뜬다.
- 뷰어는 `tU-` 폰의 보고로 **시계를 바꾸지 않는다**(재시작 폰의 1:40:00 에 끌려가면 안 됨) — 대신 "미동기화"로 표시하고,
  두 폰이 5초 넘게 어긋나면 "폰 시간 불일치"를 띄운다. `arduinoID` 가 없던 구버전(`__t__`)은 믿을 만한 것으로 취급한다(하위호환).

### 종료는 되돌릴 수 없다 (v142)

엔딩(거리 pin26)·TIME OUT 이면 **폰과 뷰어 모두 타이머가 끝까지 멈춰 있어야 한다.**
그런데 폰은 `clearInterval` 만 하고 `timerInterval`·`endTime` 을 그대로 뒀고, 뷰어는 아예 멈추지도 않았다.
그래서 이런 일이 났다:

| 증상 | 원인 |
|---|---|
| 멈췄다가 중간에 다시 흐름 | `endTime` 이 남아 있어 **`restoreTimer()`** 가 되살림. 이건 ws 재연결마다 호출된다 |
| 시간 적용·자동동기화 뒤 다시 흐름 | `timerInterval` 이 truthy 로 남아 `_gmApplyTime` 이 "진행 중"으로 오해하고 `startTimer()` 호출 |
| 뷰어가 처음부터 안 멈춤 | 뷰어는 엔딩에 **플래그만** 켰다. 시계를 멈추는 코드가 없었다 |
| 뷰어가 멈췄다가 다시 흐름 | 폰이 계속 `__time__` 을 보냈고(위와 같은 이유), 뷰어는 보고를 받을 때마다 `tStart()` 를 불렀다 |

**규칙**: 정지를 "상태"로 남기고(폰 `timerStopped`, 뷰어 `ended`), **켜는 쪽이 전부 그 값을 확인한다.**
- 폰: `stopTimerForGood()` 이 `timerStopped=true` + `timerInterval=null` + `endTime=null` 을 한 번에 한다.
  `startTimer()`·`restoreTimer()` 는 정지 상태면 즉시 반환한다.
- 뷰어: 엔딩이면 `tPause()` + 예약된 137초 시작 취소. 그 뒤 폰 보고는 **값만** 반영하고 절대 `tStart()` 하지 않는다.
- 해제는 **초기화(10탭·리셋)로만** 된다. 다음 팀은 정상 진행된다.

### 사고 재시작은 아무것도 지우지 않는다 (v143)

`__reset__` 부팅 통보에는 **두 가지 서로 다른 사건**이 섞여 있었다.

| 사건 | 원하는 결과 | v142 까지의 실제 |
|---|---|---|
| 아침 부팅 · 팀 교대 새로고침 | 다른 폰·뷰어도 깨끗이 초기화 | ✅ 맞음 |
| **게임 도중 태블릿이 꺼졌다 켜짐** | 조용히 진행만 따라잡기 | ❌ 멀쩡한 다른 태블릿이 대기화면으로 가고 뷰어도 지워짐 |

두 번째가 2026-08-05 사고다. 지워진 폰이 곧 **시간의 기준(tS-)** 이었으므로,
재시작한 폰은 시간을 물어볼 상대조차 잃어 영영 1:40:00 에 머물렀다.

**규칙**: 부팅 통보는 즉시 보내지 않고 **6초 유예**한다. 그 사이 "게임이 이미 돌고 있다"는
증거가 보이면 통보를 **취소**하고 `__boot__`(로그용)만 보낸다.

| 증거 | 어디서 |
|---|---|
| 스냅샷에 `streetmega-2 pin22` 가 이미 `on` | `slaveRegister` (5초 주기) |
| `tS-` 폰의 `__time__` / `__timeres__` 도착 | 다른 태블릿이 살아서 시간을 알고 있다 |

⚠ **10탭·원격 초기화로 인한 새로고침(`_gmBootWasReset`)에서는 이 판정을 아예 하지 않는다.**
그건 "깨끗이 시작하라"는 명시적 지시라, 걸려 있는 핀에 흔들리면 안 된다.

**시작 신호 재전송에 속지 않는다.** 재시작한 폰에 GM 이 [게임 시작 신호]를 다시 보내면
v142 까지는 그걸 "내가 본 게임 시작"으로 믿고 **1:40:00 을 `tS-`(정답)로 퍼뜨렸다**
— 뷰어 시계까지 처음으로 되돌아가고, 그 폰은 두 번 다시 남의 시간을 받지 않는다.
그래서 `pin22` 라이브 관측은 아래를 모두 통과할 때만 신뢰한다.

1. 이 폰이 **아직 게임 시작을 모르고 있었다** (`pinProgress.streetmegaPin22` 가 false)
2. 부팅 판정이 끝났다 (안 끝났으면 보류했다가 판정 후 확정)
3. 이미 돌고 있던 게임이 아니었다

또한 부팅 직후에는 `__timereq__` 를 **1.5초 간격으로 8회** 더 보낸다(그 뒤 10초 주기).
10초는 손님이 틀린 시간을 알아보기에 충분히 길다.

### 종료는 두 대가 함께 (v143)

v142 는 각 폰이 스스로 확정 정지하게 만들었지만, 정지의 근거가 **"내가 종료 핀을 봤다"** 하나뿐이라
한 대가 그 핀을 못 보면(또는 그 대만 구버전이면) **그 대만 계속 흐른다** — 2026-08-05 사고.

- 종료를 본 폰이 `__end__` 로 알리고, 받은 폰은 `showEndingScreen()`/`showTimeout()` 을 실행해 함께 확정 정지한다.
- 받아서 실행한 건 **되쏘지 않는다**(핑퐁 방지). 자기 에코도 무시한다.
- **아직 시작 전(대기화면) 폰은 무시한다** — 옛 신호의 잔향으로 엔딩 화면이 뜨면 안 된다.
- 뷰어는 엔딩 뒤에도 남은시간이 계속 줄어드는 폰을 감지해 경고하고, `[⏹ 엔딩 정지 재전송]` 으로 `__end__` 를 다시 쏠 수 있다.

### 태블릿 버전은 눈에 보여야 한다 (v143)

이번 사고의 진짜 뿌리는 **"어느 태블릿이 구버전인지 GM 이 알 방법이 없었다"** 는 것이다
(v142 업로드 후 한 대만 새로고침됨). 폰은 5초마다 `__ver__` 로 자기 버전을 보고하고,
뷰어 헤더가 항상 `폰 v143 ×2` / `⚠ 버전 불일치` / `⚠ 구버전 n대` 를 띄운다.
구버전(v142 이하)은 `__ver__` 를 보내지 않으므로 `__status__` 대수와의 차이로 잡힌다.

## 불변식
- 모니터링은 서버 무수정. 조작만 simPin 패치+재시작(손님 없을 때).
- 종료(엔딩·TIME OUT)는 되돌릴 수 없다. 초기화 전까지 폰·뷰어 모두 시간이 다시 흐르면 안 된다.
- master 다중접속은 실폰에 영향 없음(추가 fanout 몇 건뿐).
- 미션 표시는 **최신 단계가 항상 이긴다**. 늦게 터지는 예약이 화면을 되돌리거나 지우면 안 된다.
